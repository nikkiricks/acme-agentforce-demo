01

The constraint, and the point of view

Acme runs regulated hiring at scale. Every screening decision is one a regulator or a plaintiff's attorney can ask about two years later, which makes four questions non-negotiable: which version ran, what instructions it had, what data it could see and who granted that, and what it actually did. A PoC that cannot answer those is a science project, however good the output looks on screen.

The reflexive assumption is that governance is a tax you pay after the demo — build it fast in the UI, harden it later. This build is the argument against that. Author the agent as an Agent Script file, validate locally, publish, activate, test: every step is a sf command whose input is a file you can diff, review, and revert. Once that is true, the audit questions stop being an investigation and become a git log. The UI is a good preview window. It is the wrong place to hold the work.

This build's V1 was done entirely in the Agentforce Builder UI. When V2 opened the same org from the CLI, both prior BotVersions were Inactive and the CountCandidates action that had been demoed working in preview existed nowhere as committed metadata — zero GenAiFunctionDefinition records. A working demo had been built and then silently lost. No error, no warning, no way to tell from the UI. That is the failure mode source control makes structurally impossible.

Best moment

sf agent test. All four commands describe the full lifecycle in their own help text and cross-reference each other by name, so reading one tells you the next command to run. The newest surface in the build has its best docs — which complicates the easy "new means undocumented" story.

Worst moment

sf agent publish authoring-bundle and sf agent test run --wait both exit non-zero with fetch failed on runs that fully succeeded. The publish that reported failure had created BotVersion 3, registered both function definitions, and logged a Succeeded deploy — provable only by pulling the deploy ID out of the error payload and cross-querying the org. An exit code that lies is worse than a missing flag, because CI is built to trust exactly that signal.

The same pattern one layer deeper, and the costliest finding in the build. Fixing a routing bug meant editing the router's instructions, publishing, activating, testing. Both publish and activate reported success the instant their deploy landed — but the classifier model behind the router took several more minutes to honour the change. Four consecutive publish–activate–test cycles reproduced the original bug before a fifth attempt, with no new publish and only elapsed time, finally passed. Nothing in any command's output distinguishes "activated" from "the router now reflects your edit."

Four more worth carrying into a customer conversation

AiAuthoringBundle cannot be retrieved or deployed through the Metadata API at any API version this org supports — sf agent publish is the only path. The bundle's folder name must equal the developer_name compiled from inside the .agent file, and -n/--api-name is ignored for that lookup; root-caused by reading the installed plugin's source. The agent test spec's description field has an undocumented 255-character server-side cap that fails with data value too large. And the interactive generate test-spec wizard offers org-suffixed topic and action names that the runtime evaluator can never match, so following the tool's own suggestions builds a permanently-failing suite.

None of these are reasons not to build this way. They are the reasons a customer wants a partner who has already hit them.

04

Security findings

The security story is not a slide. It is a test that runs.

Zero data by default, proven non-vacuously

SecurityBeatTest inserts a candidate Contact, asserts the admin can see it as a positive control, then runs as a freshly created Minimum Access user and asserts that specific record is invisible. 2/2 pass.

The second half matters more than the result. The first version of this test was vacuous and passed anyway. Without SeeAllData, an Apex test sees no pre-existing records for any user, admin included — so "the restricted user sees nothing" was true by construction, and would have passed identically if that profile had full Contact read. A code review caught it; no documentation would have. It stays in the journal as a failure, because a green check that proves nothing is exactly what this PoC is arguing about.

Deliberate, declared grants

The agent reads the roster because SystemModeWithoutSharing is one line in the flow XML, in the diff, in the review. The org itself flags it — the deploy returned an informational warning that this mode grants view and edit on all data. Expected, intentional, on the record. In V1 the same grant went in through a UI menu and nobody could later determine whether it was the fix that worked.

Immutable versions, and the decoy user

BotVersion 7 is Active; v1 through v6 remain Inactive, and only one version can be active at a time. The agent's default_agent_user is locked after first publish, and this org contains a near-twin user differing only by numeric suffix — during V1 an assistant edit swapped to the decoy and broke validation. In V2 the access: block is a line in a file that no tool rewrites, verified byte-for-byte unchanged across the entire delta.

That is the point of running the ladder as a suite instead of a script someone retypes: when the agent is wrong, one command says exactly where.

06

The art of the possible

Each of these is an increment on machinery that already works, not a rebuild.

  • Auto-screen on arrivalA record-triggered flow fires the same screening topic the moment an application lands, so the recruiter opens a triaged queue instead of an inbox. The agent is already invoked by flow; only the trigger changes.
  • Candidate-facing agentThe same governed pattern pointed outward — status, scheduling, follow-up questions — with the never-auto-reject and equitable-treatment rules enforced by the same instructions the recruiter's agent uses.
  • ATS integrationToday the requisition is pasted in. In production it arrives from the ATS and the screening result posts back; the profile text already moves through a declared flow interface, which is where the connector attaches.
  • AgentExchangeA regulated-hiring screening agent packaged with its flows, permission model, and test suite. The tests travel with it, so the buyer verifies governance before installing rather than trusting a demo.

You do not have to choose between shipping fast and shipping something you can defend to a regulator. The UI path cost a lost build, an hour on an inactive flow version, an import that silently mapped resumes onto the wrong object, and a root cause never confirmed. The CLI path produced a live, activated, tested agent with a complete audit trail — and a scorecard honest enough to include its own failures. Governance is not the tax on the demo. It is what makes the demo mean something.
